# 同类系统对比

版本：v0.24 · 状态：调研 · 日期：2026-11-19

本文把 Genvagent 与几个同类系统做对比：它们各自解决什么问题、怎么解决、和 Genvagent 有什么不同，以及哪些做法值得借鉴。术语见[概念模型](concepts.md)。

调研来源：

- dsh-superagent 和 DS-Bot：读了仓库中的设计文档（2026-11-19 的 HEAD）。
- 其余系统：依据公开文档和已有了解，没有逐一读代码；细节以各自的最新文档为准。
- pi 的对比已写进[概念模型](concepts.md)和[Agent Harness](agent-harness.md) §7，这里只放进汇总表。

## 1. 对比维度

| 维度 | 关心的问题 |
| --- | --- |
| 定位 | 面向谁，解决什么问题 |
| 执行模型 | 谁来驱动 Agent Loop；多任务怎么并发；Router 会不会被阻塞 |
| 持久化与恢复 | 状态存在哪里；进程崩溃后怎样接着做；外部副作用会不会重复 |
| 上下文管理 | Context 的结构；压缩、回退、分叉怎么做 |
| 长期记忆 | 跨对话记什么；怎么写入、检索、遗忘；能否溯源 |
| 多 Agent 协作 | 任务怎么委派；结果怎么交回 |
| 授权与人工介入 | 谁可以让 Agent 干活；什么时候需要人 |
| 部署形态 | 单机还是集群；对 Host 的依赖 |

## 2. dsh-superagent

[deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype) 是 DeepSeek Harness（DSH）的插件，研究原型。它是一个面向单个 GitHub 仓库的主动式编码 Agent：监听 GitHub 和飞书的事件，有人请求时开工单、干活，然后回到原对话交付结果（例如一个 PR）。

核心原则是**尽量少占用人的注意力**：只在被请求或规则允许时行动，只在有人必须行动或能用上结果时说话。

### 2.1 关键设计

- **领域模型以"授权"为中心。** 事件流是 Source → Trigger → Thread → Eval → Ticket → Assignment → Executor。
  - Eval 分两层：确定性的准入（Gate），加模型研判（Assessment）。
  - 接单时生成不可变的 Mandate，记录策略版本、范围、强度（显式或推断），以及发起人。
  - 范围变大就要新开工单。
- **订阅与扇出。** Ticket 订阅相关的 Thread。之后 Thread 上人的消息会直接投递给已有工单，不再走 Eval。这样后续讨论能自然到达执行者，不必再 @ 一次 Agent。
- **执行。**
  - 每个 Ticket 对应一个 DSH Executor Session 和一个工作目录（通常是 `git worktree`）。
  - 主 Session（orchestrator）只做研判、派工和回复，相当于我们的 Router。
  - 新消息在下一个步骤边界投递给 Session。前台 shell 命令 5 秒后转到后台，让 Agent 能及时收到新消息。
- **并发控制。** 用 Worker 槽位限制并发，另外预留一个槽位给人的消息或状态查询。新任务再多，也不会堵住人对已有工单的跟进。
- **持久化。**
  - 单进程，只用一个 SQLite 文件。Engine 的每条命令在一个事务内完成。
  - 外部动作（投递、回复、启动执行）先写入 `effect` 和 `outbox` 表，提交后再执行，即事务性 outbox。
  - 重试采用指数退避。
- **恢复。** 重启时，正在执行的 Assignment 以"host restarted"结束，然后带上一段恢复说明重新启动。说明要求 Agent 在重复任何外部动作之前，先检查目录、git 历史和 GitHub。也就是说，外部副作用的去重靠 Agent 自己判断，不靠幂等键。
- **人工介入。** Ticket 的阶段由"在等什么"决定，例如等人回答、等人评审、受阻、失败。面板只显示需要人处理的事项。
- **记忆。** 没有独立的长期记忆系统。上下文就是 DSH Session 的历史，跨工单的事实由主 Session 用 `note` 转交。

### 2.2 与 Genvagent 的对照

| 方面 | dsh-superagent | Genvagent |
| --- | --- | --- |
| 授权 | 完整的 Policy、Mandate、Gate 模型，是它的核心 | 列为待定 |
| 执行单元 | Ticket ↔ 一个 DSH Session，绑定固定 | Task ↔ Context（Router 选定 contextId），执行实例可变 |
| 调度 | 单进程槽位，人的消息优先 | 多实例 × 槽位，竞争拉取 + 软亲和 |
| 消息投递 | 步骤边界投递到 Session 收件箱 | 步骤边界读取任务队列，确认在提交之后 |
| 持久化 | 单个 SQLite + 事务性 outbox | Harness 执行存储 + Memory 版本链，两套存储 |
| 恢复 | 重启后带恢复说明重跑，靠 Agent 自查 | 从链尾元数据得知 stepId 和已纳入的消息，补做确认；工具用幂等键 |
| 上下文 | DSH Session 历史，不可分叉，没有版本 | 线性版本链，可从任意版本分叉、回退 |
| 长期记忆 | 无 | 独立的 Memory System，可溯源、带墓碑 |
| 部署 | 单机、单仓库 | 单机或集群 |

**它的优点**

- 领域概念少而准，每条规则都写明了"为什么存在"。
- 授权和人工介入考虑得非常完整，这正好是 Genvagent 的空白。
- 单进程加单个 SQLite 让一致性简单：一个事务就能覆盖状态变更和待执行的外部动作。
- 已经在 DSH 上跑通了 Hosted 模式。

**它的不足**

- 只能单机运行，Worker 的规模受一个进程限制。
- Context 不能分叉，也没有版本，回退只能靠 git 和 Agent 自己。
- 没有跨任务的长期记忆。
- 崩溃恢复依赖模型自查，不是确定性的去重。

## 3. DS-Bot

[Fei2411/DS-Bot](https://github.com/Fei2411/DS-Bot) 也基于 DSH，既可以作为插件，也可以作为独立的桌面应用。它面向个人用户，提供一支持久化的 Bot 团队：每个 Bot 是长期存在的身份，有自己的模型、工作目录、记忆和浏览器；Bot 之间可以私聊派活，也可以在群聊里协作。数据都留在本机。

### 3.1 关键设计

- **一个 Bot 是一个长期身份，对话由多段 DSH Session 组成。** 上下文接近上限时，由轻量的"上下文管家"（一次单独的小模型调用）在两种做法中选一种：
  - **压缩（compact）**：活还没做完时，原地压缩成检查点（摘要 + 用户原话），然后继续。
  - **换段（switch）**：活告一段落时，写一份交接笔记，在新的 Session 里接着做。
  - 压缩次数越多，管家越倾向于换段，因为"摘要的摘要"损失更大。
  - 旧段完整保留，用 SQLite FTS5 全文检索，并以锚点回查原文。
- **阈值全部跟着模型走。** 不写死 token 数。按模型窗口计算硬线（0.95 × 可用窗口）和预判线（0.8 × 可用窗口），在回合结束时判断，或在回合中途越过硬线时判断。
- **记忆。**
  - 记忆是 Markdown 文件，每行一条，带来源和日期。分三个范围：Bot 自己、群、团队。
  - 每个回合结束后，有一次自动的"记忆整理"负责增、改、删。
  - 所有改动写入 `journal.jsonl`，可以撤销；`pending.json` 保证一次改动不会只写一半。
  - 记忆不是指令，看起来像密钥的内容会被拒绝。
- **为前缀缓存设计。** 记忆在每个 Session 第一次渲染时冻结进系统提示词，之后保持逐字节不变。别人后来的改动以增量消息的形式在步骤之前送入，因此不会打破提供方的前缀缓存。
- **派活是一棵树。**
  - 下级的结果没交回时，上级的回复先不交出。下级交回后，结果自动往上走。
  - 只拦截"给正在等这件活结果的 Bot 发消息"这一种结构性错误，不靠跳数或条数上限防绕圈。
  - 未读消息按发件人合并成一条。
- **消息账本。** 群消息和 Bot 之间的消息先写入只追加的 JSONL 账本，其他地方都从账本读，作为唯一的写入口。
- **关掉 DSH 子代理。** 理由是子代理用户看不见、停不了，换段时还会被连带取消，结论丢失。需要并行时，就让多个 Bot 同时干。
- **其他。**
  - 同一个 Bot 可以开多个并行 Session。
  - 本地 Agent CLI（Claude Code、Codex 等）可以接入为 Bot。
  - 只有一个进程能写团队数据，其他进程只读。

### 3.2 与 Genvagent 的对照

| 方面 | DS-Bot | Genvagent |
| --- | --- | --- |
| 定位 | 个人桌面上的 Bot 团队，重交互和界面 | 后台持久化执行 + 统一记忆服务 |
| 上下文超限 | 管家二选一：压缩，或换段加交接笔记 | Harness 发起、Memory 执行压缩；换路线用分叉 |
| 历史 | 旧段归档，可以全文检索 | 版本链完整保留，可从任意版本分叉 |
| 记忆格式 | Markdown 条目，三个范围，日志可撤销 | 结构化记忆条目，有修订、墓碑和溯源 |
| 记忆写入 | 回合后整理，加 Bot 工具 | 后台提炼，加 Harness 提出候选 |
| 前缀缓存 | 核心约束，专门设计 | 步骤版本只追加，天然命中；分叉共享前缀；尚未写成显式不变量 |
| 多 Agent | 派活树，结果自动向上冒泡 | Router 派子任务，结果消息加 reply-to |
| 持久化 | 本机文件 + JSONL 账本，单写入进程 | 执行存储 + Memory，可以多实例 |
| 授权 | Main Bot 和普通 Bot 的角色，私密 Bot，用户批准 | 待定 |

**它的优点**

- 对"上下文长期增长"的处理最成熟：压缩与换段二选一，并考虑摘要质量的衰减。
- 认真对待前缀缓存和成本，这是生产中最实际的约束之一。
- 记忆可以撤销，并且有明确的写入和读取权限矩阵。
- 派活树让结果自动交回上级，从结构上避免绕圈，不依赖数量上限。

**它的不足**

- 本质上是单机、单用户应用，不面向多实例部署。
- Bot、群、段、账本、批次等概念多，规则分散在几十份 plan 里。
- 记忆是自由文本条目，溯源只到"来源锚点"，可信度没有分级。
- 执行恢复主要依赖 DSH Session 本身，没有租约和隔离令牌（fencing token）这样的语义。

## 4. 其他同类系统

| 系统 | 类别 | 要点 | 与 Genvagent 的关系 |
| --- | --- | --- | --- |
| [LangGraph](https://docs.langchain.com/oss/python/langgraph/persistence) | Agent 框架 + 持久化 | Checkpointer 在每个步骤保存状态快照，按 `thread_id` 组织；可以从历史检查点恢复或分叉（time travel）；有中断，支持人工介入；另有跨 thread 的 Store 存放长期记忆 | "每个步骤一个快照、可以从历史分叉"与我们的版本链几乎一致。不同之处在于，它的状态是整张图的状态，并且通常在单进程内运行 |
| [Temporal](https://temporal.io/blog/announcing-openai-agents-sdk-integration) + Agents SDK | 通用持久化执行引擎 | Workflow 按事件历史确定性重放；LLM 调用和工具作为 Activity 执行，自动重试；任务队列加 Worker；已集成 OpenAI Agents SDK、LangGraph、Vercel AI SDK | 我们的 Harness 在自己实现 Temporal 已有的部分：租约、重投、Worker 池、等待条件。Temporal 可以作为执行存储的候选，但它的"确定性重放"与 LLM 的不确定性需要用 Activity 隔开 |
| [Letta](https://www.letta.com/blog/agent-memory)（原 MemGPT） | 有状态 Agent 服务 | 核心记忆（memory block，常驻上下文，Agent 可以自己改写）加归档记忆（需要检索）；sleep-time agent 在后台整理记忆；服务端持久化 Agent 状态 | 与我们的 Memory System 定位接近。它的记忆可以直接被 Agent 改写；我们走"提出候选 → 校验 → 发布"，更保守，但溯源更强 |
| Mem0、Zep（Graphiti） | 记忆层服务 | 从对话中抽取事实并检索；Zep 用带时间的知识图谱，记录事实何时有效、何时失效 | 可以作为 Memory 知识层的实现参考。Zep 的时间有效性与我们的 superseded 状态对应 |
| Claude Code、OpenHands 等编码 Agent | 单 Agent 运行时 | 会话日志（JSONL、事件流）；上下文接近上限时自动压缩；子代理在独立上下文中执行，只交回结论 | 属于 Host 一类，是我们的集成对象，而不是竞品。"子代理只交回结论"与我们"结果消息只带版本引用"一致 |
| pi | 单 Agent 运行时（Host） | JSONL 记录树、`compaction`、`branch_summary`、单个写入者 | 已在概念模型中对比；导入规则见 [Memory System](memory-system.md) §4 |

## 6. Genvagent 的定位与优缺点

**优点**

- **执行与记忆分离，依赖单向。** 记忆服务可以独立部署，并服务多个 Host 和应用。前面几个系统大多把两者混在一起，或者只做其中一半。
- **可分叉的 Context 版本链。** 回退、分叉、跨 Session 复用都是一等操作，历史不被改写。DS-Bot 的"换段"和 superagent 的"重开"都只是它的特例。
- **确定性的恢复语义。** 先在 Memory 提交，再在 Harness 确认；租约加隔离令牌；工具使用幂等键。比"让模型自查"更可靠。
- **记忆可以溯源，遗忘有墓碑。** 适合多用户、需要合规的场景。
- **与 Host 无关。** 用 Hosted 或 Standalone 两种模式接入已有的 Agent 程序，不重写 Agent Loop。

**缺点与风险**

- **只有设计，没有实现。** 前面几个系统都有代码在跑，我们的设计还没有被实践验证过。
- **两套存储加消息队列，运维和一致性都更复杂。** superagent 一个 SQLite 事务就能解决的问题，我们需要跨系统排好写入顺序。
- **步骤执行依赖 Memory 可用。** 每个步骤提交一次版本，延迟是毫秒级，相对 LLM 调用可以忽略；但 Memory 不可用时步骤会停下（`UNAVAILABLE`）。
- **授权和人工介入还是空白。** 这在 superagent 里是核心。
- **依赖 Router 选对 Context。** 选错会误沿用或误新建。已采取的措施：沿用靠从列表中选择而不是名称匹配，外部实体用确定性名称，拿不准时新建（见[概念模型 §4.2](concepts.md#42-指派规则)）；新建时的相似提示和 Worker 的不匹配报告尚待细化。
- **自己实现持久化执行的成本高。** 租约、重投、等待条件、DLQ 都需要自己做，而 Temporal 这类引擎已经提供了这些。

## 7. 值得借鉴的做法

按优先级排列，建议在后续细化时逐条决定是否吸收。

1. **授权模型（来自 superagent）。** 把"谁能让 Agent 干什么"建模为不可变的 Mandate，记录在 Task 上：发起人、范围、强度、策略版本。范围变大就新开 Task。这可以直接填补概念模型 §8 的"授权"空白。
2. **压缩与新开 Context 二选一（来自 DS-Bot）。**
   - 活没做完：压缩，继续在同一条链上。
   - 告一段落：新建 Context，以交接笔记为初始内容，与旧 Context 通过分叉关系相连。
   - 压缩次数多了就倾向于新开。
   - 这只改变 Harness 的策略，不改变 Memory 的接口。
3. **把前缀缓存写成显式不变量（参考 DS-Bot）。** 我们的设计已经满足：步骤版本只追加，分叉出的 Context 与来源共享前缀，只有压缩、回退、编辑会改变前缀。需要写明的是：
   - 版本快照渲染成模型输入时逐字节确定。
   - Context 中途不改指令和工具配置；确实要改时，按编辑处理，接受缓存失效。
   - 记忆、画像的后续变化以追加消息送入，不改写系统提示词（DS-Bot 的"冻结 + 增量"做法）。
4. **人的消息优先（来自 superagent）。** Worker 池为人的跟进消息预留容量，后台新任务不能堵住它。
5. **结果自动交回上级（来自 DS-Bot）。** 子任务未完成时，父任务的结果先不交出。禁止"给正在等这件活结果的 Task 发消息"，从结构上避免循环。这可以写进 Task 的等待条件和委派规则。
6. **执行存储考虑现成引擎（来自 Temporal）。** 评估用 Temporal 或类似引擎实现执行存储和队列，而不是自己实现。LLM 调用和工具作为 Activity，Memory 提交也作为 Activity；我们的幂等键设计正好与之兼容。
7. **记忆的读法分层（来自 Letta 和 DS-Bot）。** 常驻（始终进入上下文）、增量、自动召回、按需检索，各有额度。这可以细化 `recall` 和 `getProfile` 的使用方式。
8. **记忆改动可以撤销（来自 DS-Bot）。** 记忆条目的修订本身就保留了历史，可以补一个面向用户的"撤销某次修订"操作。

## 8. 待细化

- 授权模型是否采用 Mandate 形式，以及它与 Task、Context 的关系
- 换 Context 的判定交给谁：Harness 的规则、一个小模型，还是 Host
- 前缀缓存不变量写进概念模型 §6，以及记忆在 Worker 提示词中的位置
- 执行存储自建与采用 Temporal 的比较
